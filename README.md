# toklens

看清大模型请求里的 **token 花在哪**。

不估算、不套经验系数——直接调 `tiktoken` 真数，然后把一次请求拆成
「每一轮都在重发的固定部分」和「真正的对话部分」，最后把几种上下文裁剪
策略重放一遍比较累计输入。

```
pip install tiktoken
python -m toklens.cli audit requests.jsonl
```

---

## 为什么需要这个东西

多轮对话的成本优化，大部分文章都在讲同一件事：**裁历史**。

我拿一个客服机器人的 10 轮对话真数了一遍，结论不太一样：

```
请求数 10   编码器 o200k_base
────────────────────────────────────────────────────────────────────
  输入 token 合计              4956
  单轮输入                      249  →         738   末轮是首轮的 3.0 倍

  ★ 公共前缀长度                246  token
    也就是每一轮都在原样重发的部分（含角色标记）
    累计                       2460  占全部输入 49.6%
```

**一半的输入，是每一轮原样重发的那段。** 十轮对话本身加起来只占一成。

> **这份输出可以直接复现**：`toklens audit examples/requests.jsonl`。
> 换一份会话，占比会在 **49.5%～49.6%** 之间小幅浮动——**这个结论对输入不敏感**，
> 这比精确到小数点后一位更有价值。

你为了省那一成的历史记录写了一堆窗口逻辑，而系统提示和知识库每轮
雷打不动地重发——**优化顺序应该是反过来的**。

`toklens audit` 就是自动把这段找出来：把同一次会话的每一轮请求都喂进去，
算它们的**公共前缀**，那个长度就是每轮都在重发的部分。

## 三个命令

### `count` —— 数 token 与中文密度

```bash
toklens count examples/conversation.json
```

```
编码器 o200k_base   （可用 --encoding / --model 改）
────────────────────────────────────────────────────────────────────
  来源                             token      字符      汉字   token/汉字
  conversation.json                964    1687     819       1.18
```

**为什么给的是「每汉字」而不是「每字符」**：中英混排时这两个数能差一倍
以上。`conversation.json` 里有大量 JSON 标点，所以摊到每个汉字上是 1.18；
纯中文技术说明一般在 0.8 左右。

> 顺带纠正一个流传很广的说法：**「1 个汉字 ≈ 1.5～2 个 token」是错的。**
> 实测（`o200k_base`）中文技术说明约 **0.84 token/汉字**，客服话术约 **0.69**；
> 换成 `cl100k_base` 才是 1.17 / 1.00。差得不是一点半点，
> 用它估成本会高估一倍。

### `audit` —— 找出每轮重发的那段

输入是一组请求（JSON 数组或 JSONL，每项是 OpenAI 风格的请求体）：

```jsonc
{"model": "gpt-4o", "messages": [{"role": "system", "content": "..."}, ...]}
```

```bash
toklens audit examples/requests.jsonl --show-breakdown
```

加 `--show-breakdown` 会额外按 role 列一下第一轮的构成：

```
  第一轮的构成：
    system           224
    user              22
    合法固定部分占比      91.1%   （按 role=system 统计）
```

**结尾会给一句结论**，直接说该动哪一边：

```
  结论
  固定部分占 50%，和对话部分量级相当，两边都值得看。
```

分档是 50% / 25%：超过一半就直接说「先别裁历史」；低于四分之一才说
「裁历史是这里收益最大的方向」。

> **公共前缀是 0 的时候要留意。** 那说明每次请求的开头都不一样——
> 常见原因是把时间戳、随机 ID 或「当前时间」放进了系统提示的开头。
> 这不但浪费 token，还会让 **prompt 缓存彻底无法命中**（缓存是按前缀匹配的）。
> `audit` 会专门把这种情况点出来。

### `sim` —— 比较上下文裁剪策略

```bash
toklens sim examples/conversation.json --window 3
```

```
轮数 10   编码器 o200k_base
────────────────────────────────────────────────────────────────────
  固定部分（system + knowledge）       214 token
  摘要（仅 summary 策略使用）           93 token
  对话本身合计                         449 token

  累计输入 token
  full         4326        基准
  window       3343    +22.7%  窗口 3 轮
  summary      3901     +9.8%  窗口 3 轮 + 摘要
  none         2247    +48.1%

────────────────────────────────────────────────────────────────────
  怎么读
    纯窗口 3 轮          省 22.7%（相对全量历史）
    窗口 + 摘要                省 9.8%
  ★ 摘要比纯窗口贵 +16.7%——它是在窗口之外额外加上去的，
    买的不是省钱，是「早期上下文不丢」。
    不带历史                   省 48.1%（会丢失上下文，只是下限参考）
```

## 一个容易算错的地方：摘要不省钱

**摘要在请求里的位置，不是替换窗口内容，而是额外加上去：**

```
请求 = 系统提示 + 知识库 + 【摘要】 + 窗口内历史 + 本轮输入
```

所以它每轮都在**增加**成本，**永远比纯窗口贵**。上面那个例子里贵 16.7%。

摘要买的不是省钱，是**早期上下文不丢**——那是质量问题，不是成本问题。
它省钱的对比对象是「全量历史」，不是「纯窗口」。这两者混起来算，
结论会整个反过来。

`sim` 把四种策略放在一起，就是为了让这件事一眼看清：

| 策略 | 含义 |
| --- | --- |
| `full` | 全量历史，每轮把所有历史都发一遍（基准） |
| `window` | 滑动窗口，只带最近 N 轮原文 |
| `summary` | 窗口 + 摘要（摘要**额外**加上） |
| `none` | 不带历史（对照组，只用来给出「裁历史的天花板」） |

---

## 这套数字对谁有效

**说得直白一些，免得你拿它做错决定：**

- **只对使用同一套 BPE 词表的模型准确。** 也就是 OpenAI 系（`o200k_base` /
  `cl100k_base`）。Claude、Gemini、DeepSeek、Qwen 各有自己的分词器，
  `tiktoken` 数出来的中文数字会**偏**——通常偏得不多，但不足以做精确计费。
  要精确，用各家自己的 tokenizer。**这个工具刻意不做「估算」**，
  因为估算出来的数不能用来做成本判断。
- **`--overhead`（每条消息的固定开销）默认 4**，这是 OpenAI 的量级。
  不同厂商不一样，短消息很多时这个参数影响很明显。**建议用你自己的接口
  实测一次再改。**
- **比例是可迁移的，绝对值不是。** 「固定部分占了一半」这个结论在别的
  分词器下基本成立（因为它是比例）；但「214 token」这种绝对数字换了模型
  就不准了。
- **不带历史的那一栏只是下限参考**，不是可选方案——它把上下文丢了。

## 示例数据

`examples/` 里是一个 10 轮的电商客服对话（真实的对话形态，不是 lorem ipsum）：

| 文件 | 用途 |
| --- | --- |
| `conversation.json` | `sim` 的输入：`{system, knowledge, summary, turns}` |
| `requests.jsonl` | `audit` 的输入：10 个完整请求体，每轮都带全部历史 |

`requests.jsonl` 模拟的是最常见的写法——每轮把全部历史发一遍，
开头永远挂着同样的 `system` + `knowledge`。这就是那个「公共前缀」。

## 设计取舍

- **不做估算，只做计数。** 估算工具很多，但它们给不出能用来做判断的数。
- **不做模型调用的代理。** 它不联网、不需要 API key，只处理本地文本和 JSON。
- **`audit` 用「公共前缀」而不是「`role == system`」来判断固定部分。**
  后者会漏掉那些以 `user` 角色塞进去的知识库或少样本示例——那在实际项目里
  非常常见。前者直接看字节，不猜意图。
- **角色标记算进前缀。** 否则两条 `role` 不同但正文相同的消息会被误判成相同。
  代价是前缀比「纯文本长度」多几个 token，可以接受。
- **`sim` 的窗口参数是「轮」，一轮 = 用户一句 + 助手一句。** 内部对每轮的
  token 数单独记账。这里曾经有过一个 bug：窗口切片写成了 `[-window*2:]`，
  而记账是每轮一个元素，于是实际保留了 2 倍轮数，把「摘要比纯窗口贵多少」
  算错了。现在有回归测试钉着这组数字（`tests/test_toklens.py`）。
